## A. Current architecture

`frontend/src/main.tsx` renders React 19 in StrictMode; `frontend/src/App.tsx` registers landing/login/waiting, SuperAdmin, CollegeAdmin, HOD, faculty and student routes. Redux Toolkit (`frontend/src/store/index.ts`) stores student, faculty and HOD slices; CollegeAdmin and SuperAdmin use component state, localStorage and direct Supabase calls. Request clients are `studentApi.ts` (fetch, `{success,data}`), `facultyApi.ts` (axios, bare JSON), `hodApi.ts` (fetch), `collegeService.ts` (PostgREST plus fetch) and `services/api/collegeProfile.ts`. Authentication is Firebase Web SDK **plus** localStorage role/token snapshots; the Supabase browser client in `frontend/src/config/supabase.ts` uses a public publishable key, not a Firebase-to-Supabase JWT bridge.

`backend/src/server.ts:49-53` exports Express without `listen()` on Vercel; locally it connects and listens. `backend/src/app.ts:21-93` installs Helmet, CORS, a per-instance in-memory rate limiter (exempts `/api/auth/sync`), 1 MB request limits, and routers: `/api/auth`, `/profiles`, `/approvals`, `/users`, `/colleges`, `/college-admin`, `/faculty`, `/roles`, `/audit`, `/student`, and HOD at `/api/hod` plus resource aliases under `/api`. Prisma singleton in `backend/src/config/database.ts` connects to Supabase PostgreSQL; faculty also uses raw SQL for non-Prisma tables and module-local caches. `backend/src/config/env.ts` validates DB/Firebase/server variables, but not `DIRECT_URL` even though schema requires it for migration tooling. Root `vercel.json` uses legacy `builds`/`routes` with `@vercel/node` and `@vercel/static-build`; `frontend/vercel.json` rewrites only for a separately deployed frontend. Actual deployed build selection, runtime version, region and connection-string settings **must be checked in Vercel**, not inferred from local files. `backend/package.json` says Node `>=18`; it does not pin a Vercel major version.

## C. Database architecture

One Supabase PostgreSQL public schema contains **24 ordinary tables**, **248 columns**, **29 FK constraints**, **51 indexes**; no public views, public SQL functions or non-internal public triggers found via `information_schema`. Five extensions: `pg_stat_statements`, `pgcrypto`, `plpgsql`, `supabase_vault`, `uuid-ossp`. Prisma schema has **18 models** (10 governance/identity + `AuthedUser` + 7 academic models), **not** the “16 total” stated in vault notes. Six live tables (`attendance_records`, `attendance_sessions`, `class_timetables`, `faculty_reminders`, `faculty_timetables`, `_prisma_migrations`) are not represented by Prisma domain models. The initial migration `backend/prisma/migrations/20260929031542_add_college_profile_fields/migration.sql` assumes UUID keys/camelCase college fields; the live database and current Prisma schema use text IDs and mixed snake/camel-case. Only **one applied Prisma migration** was visible. `backend/src/scripts/init_faculty_tables.ts`, standalone `backend/*.js` schema/policy scripts and direct SQL explain additional drift; do not rerun a historical migration on production blindly.

The actual FKs relate `users`/`profiles`/`user_roles`/`account_approvals` to `colleges`, separately `authed_users` to `colleges`/`departments`/`classes`/`subjects`, and class→batch→program→department→college. Attendance sessions→class/faculty/subject; records→session/student. `faculty_timetables`, `faculty_reminders` and `class_timetables` have **no declared FKs** in live metadata, despite UID/class ID fields. `classes.class_rep_uid` also has no FK. Composite unique indexes: `departments(college_id,code)`, `attendance_sessions(class_id,date,period)`, `attendance_records(attendance_session_id,student_uid)`, `user_roles(userId,roleId)`, `role_permissions(roleId,permissionId)`; single unique indexes also cover emails, `colleges.code`, names and Firebase UID. No unique constraint on college+department name, student register number scoped to college, or `(class_id,day_of_week,period)` timetable slot was seen. Review business rules before adding them.

**All 29 live FKs (child column → parent PK; grouped by child table):** `academic_years.college_id → colleges.id`; `account_approvals.userId → users.id`, `.requestedCollege → colleges.id`; `attendance_records.attendance_session_id → attendance_sessions.id`, `.student_uid → authed_users.uid`; `attendance_sessions.class_id → classes.id`, `.faculty_uid → authed_users.uid`, `.subject_id → subjects.id`; `audit_logs.actorId → users.id`, `.subjectId → users.id`; `authed_users.class_id → classes.id`, `.college_id → colleges.id`, `.department_id → departments.id`, `.subject_id → subjects.id`; `batches.program_id → programs.id`; `classes.batch_id → batches.id`, `.faculty_uid → authed_users.uid`; `departments.college_id → colleges.id`, `.hod_uid → authed_users.uid`; `profiles.userId → users.id`; `programs.department_id → departments.id`; `role_permissions.permissionId → permissions.id`, `.roleId → roles.id`; `semesters.academic_year_id → academic_years.id`; `sessions.userId → users.id`; `subjects.department_id → departments.id`; `user_roles.roleId → roles.id`, `.userId → users.id`; `users.collegeId → colleges.id`. Actual ON DELETE/UPDATE actions differ: e.g. attendance student/faculty references RESTRICT on delete and CASCADE on UID update, academic child chains CASCADE on delete, and some nullable references SET NULL. Use `pg_get_constraintdef` before migration; do not assume every FK cascades.

## D. Multi-tenant architecture

Tenant is `colleges.id` (live **text**, not necessarily UUID); academic children derive membership through the FK chain. Backend `requireTenant` only checks request user's college/optional route param and explicitly exempts SUPER_ADMIN (`tenant.middleware.ts:20-68`); services must still filter each query/ID by the resolved college. Faculty service checks only class-incharge on some routes but accepts arbitrary class ID on attendance; HOD has a first-department fallback and global year/semester lists. Browser Supabase queries take tenant IDs from props/localStorage and are **not database-enforced** because actual public policies are `USING (true)`. The frontend's cached college/role is not proof of membership. `getTenantId` with no super-admin parameter can return the superadmin's own college ID, so cross-tenant admin listing is inconsistent. Prefer deriving tenant from verified identity and joining to the requested resource within every query/transaction.

## E. Authentication architecture

Firebase authenticates the browser and is verified in main `authenticateFirebaseUser`. Main middleware reads `users`/roles, blocks PENDING/SUSPENDED; student then separately requires `authed_users.role=STUDENT`; faculty uses a **different** middleware and `authed_users`/optional `users` fallback; HOD has its own Firebase/application-JWT path. `/api/auth/sync` maintains `authed_users`, while `/api/auth/onboarding` maintains `users` + `profiles` + `user_roles` + `account_approvals`. There is no unified authoritative subject/approval status. Firebase identity is **not** forwarded to PostgREST as a verified JWT; the client uses the anonymous publishable key. UI localStorage entries `token`, `lms_user`, `faculty_auth_token`, `student_token` and related keys have different lifetimes; faculty requests prefer stored token to fresh Firebase token (`facultyApi.ts:39-68`). Server DB `sessions` records are not enforced by Firebase token verification. `Login.tsx:91-149` contains a hardcoded credential branch and fake email/password login: treat as production exposure, not as a valid second auth provider.

## F. Authorization architecture

Main routes use `requireRole`/`requirePermission` from DB-loaded roles and `requireTenant`; some inputs validated with Zod. Faculty permits FACULTY/HOD/COLLEGE_ADMIN/SUPER_ADMIN and uses a dev-token branch **even when NODE_ENV=production**. HOD `requireHODOrAdmin` resolves department and can default to the first one. Student GETs use student context. Browser-direct admin CRUD/approvals, with globally permissive live policies, circumvent all of these checks. Frontend route guards are display/navigation controls only. Backend approval `approvals:manage` is not constrained to requested role; verify seeded permission assignment and implement role-specific review scope. Positive checks: main Firebase verification, protected routes, class-incharge check on faculty roster/detail, tenant filters on many backend endpoints, validation on selected body/query endpoints.

## J. Security findings

Each finding states **severity; evidence; why/expected impact; recommended fix; files/objects**. No exploit attempt or write probe was made.

1. **CRITICAL — public read/write exposure across the whole schema.** Evidence: live `anon` grants on all 24 public tables, 15 RLS-off, 31 `public USING true` policies on 9 RLS-on tables, and anonymous SELECT actually returning `users`, `profiles`, `authed_users`, `_prisma_migrations`; `frontend/src/config/supabase.ts:3-11` publishes the key and `collegeService.ts` writes roles/data. Why/impact: unauthorized cross-college PII disclosure and potentially arbitrary tenant, role, attendance and approval manipulation; backend RBAC is irrelevant to direct PostgREST. **Fix:** incident containment/revoke anonymous table privileges, restrict exposed schema and enforce tenant/role policies or route sensitive operations through verified backend; test denials as anon, other-college and suspended users *before* restoring availability. Objects: `public.*` tables/grants/policies; files `frontend/src/services/collegeService.ts`, admin components, `backend/src` authenticated endpoints. Do not merely switch RLS on while unconditional policies remain.
2. **CRITICAL — DB credentials published in project documentation.** Evidence: `docs/Obsidian-Vault/10_Comprehensive_Project_Report.md:322-329` and `PROJECT_REPORT.md:322-329` contain full runtime/direct PostgreSQL URLs with plaintext password (intentionally not reproduced here). Why/impact: DB takeover independent of RLS if credentials are current; historical git revisions remain accessible. **Fix:** rotate DB password and all derived pooler/direct URLs in Supabase and Vercel/local secrets immediately; remove/redact documentation in a separate approved change, assess history/access/logs and incident response. Files named above plus Vercel secrets. We did not verify whether the password is still valid; treat as compromised.
3. **CRITICAL — `/auth/sync` identity takeover.** Evidence: `backend/src/modules/auth/auth.routes.ts:206-270` verifies token UID but looks up a body-supplied email and rekeys that user's `authed_users.uid`, retaining role/assignments; rate-limit exemption `app.ts:39-45`. Why/impact: any Firebase account could take over a known-email role if FK update succeeds; no SQL injection claim (bind parameters used). **Fix:** derive UID/email from verified token only; forbid rekeying a different established Firebase identity, design a separately authorized/verified preprovisioned identity claim, validate input and rate limit. Files: auth routes/service, tests; object `authed_users` and referencing FKs.
4. **CRITICAL — faculty dev bearer accepted in production.** Evidence: `backend/src/modules/faculty/faculty.middleware.ts:23-33` accepts `dev-user-<uid>` without production check, before Firebase verification. Why/impact: impersonation of known faculty/HOD/admin UID and access to faculty endpoints. **Fix:** remove branch from production and require Firebase verification/status, regression-test production NODE_ENV. Files: faculty middleware, API client/test fixtures; objects S/`users` roles.
5. **HIGH — faculty attendance IDOR and unreliable commits.** Evidence: `faculty.controller.ts:152-216` accepts class ID; `faculty.service.ts:407-436` omits ownership checks; `faculty.repository.ts:1191-1252` serially writes, catches failure, still caches and returns success; student reads DB only. Why/impact: cross-class reads/writes, false attendance and permanent data loss across serverless instances. **Fix:** verify teacher/class/college and student membership, transactionally upsert in bounded batch, fail closed; remove local attendance as persistence. Files: faculty controller/service/repository/validation; objects `attendance_sessions`, `attendance_records`, `classes`, `authed_users`.
6. **HIGH — role/approval split and cross-department HOD review.** Evidence: `backend/src/middleware/auth.middleware.ts:68-120` trusts `users` + roles; actual UI `collegeService.ts:802-832` writes S role/status; HOD `hod_temp/services/facultyService.ts:142-280` approval POST lacks target-department/role guard, may assign another department's class; main approval route only checks permission, not requested-role boundaries. Why/impact: unexpected privilege grants, contradictory access/approvals. **Fix:** one transactional authority for role/approval/status; scope review by verified college+department+allowed requestedRole, conditional PENDING update; reconcile old rows. Files: approval service/routes, HOD faculty service/middleware, CollegeAdmin and SuperAdmin components; objects `authed_users`, `users`, `user_roles`, `account_approvals`.
7. **HIGH — HOD department and data leakage.** Evidence: `hod_temp/middleware/authMiddleware.ts:135-155` chooses first department when no assignment; `hodService.ts:1010-1053` lists all colleges' academic years/semesters. Why/impact: wrong-college records and actions. **Fix:** deny missing department; filter/join all queries through verified college+department. Files HOD middleware/service/routes; objects `departments`, `academic_years`, `semesters`.
8. **HIGH — email/password path is not authentication.** Evidence: `frontend/src/pages/Login.tsx:91-149` includes hardcoded super-admin credential and any valid-looking non-super email/password producing `lms_user` without Firebase; `SuperAdmin.tsx:54-68` relies on it. Files Login, App, admin layouts/pages; objects colleges/authed_users.
9. **HIGH — bulk enrollment overwrites existing accounts.** Evidence: `faculty.repository.ts:1899-2012` finds an existing email and rewrites its class, role=STUDENT, approval status; hard-coded college for new rows. Why/impact: cross-tenant account hijack, role corruption, inconsistent student enrollment. **Fix:** class-derived tenant, reject preexisting different-tenant/non-student users, bounded validated transaction and idempotent enrollment semantics. ## R. Recommended target architecture (proposal, not implementation)

1. Firebase as sole browser identity; backend verifies token and loads a single reconciled user/role/approval authority, deriving tenant/department from DB. No localStorage role is trusted; client stores only nonauthoritative UI hints.
2. One secured, versioned backend API for admin mutations and sensitive reads. Prefer server-side scoped Prisma/SQL transactions with explicit `select` DTOs, bounded pagination and per-resource tenant/role ownership checks. If browser Supabase is retained for low-risk reads, use **genuine verified Supabase-compatible claims and deny-by-default per-tenant RLS**, not anon public access.
3. Normalize identity and academic references after a staged reconciliation/migration (preserve existing data; decide whether S or users is canonical before changes). Map live tables in versioned migrations; don't introduce a replacement DB or fake data.
4. Student dashboard/attendance and faculty today/roster should be scoped aggregate endpoints with joined/projected data and set-based writes. Short-lived shared/cacheable lookups only after defining tenant-safe keys and invalidation; never treat a process map as durable attendance.
5. Pin/check Vercel Node runtime compatibility, pooler/region/connection limit, response payload ceilings and monitoring. Measure p50/p95/p99 with safe request IDs, slow-query plans, real traffic and advisor exports **after** security containment.
